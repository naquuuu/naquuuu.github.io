(06)four tiers[ product operations ]

four tiers between a brief and an approved spec.

01

boundary audit & intake gatekeeper

  • screenpii and private credentials redacted at intake.
  • scopemoscow: must, should, and won't-have.
  • probecan a voucher exceed cart value? stack with tier points?
02

specs, flowcharts & prototypes

  • brdjourneys, edge cases, soft api contracts, state machines.
  • flowcharttransitions, retry loops, integration points.
  • prototyperesponsive html/css on real viewports.
03

acceptance governance & uat packaging

  • bactest matrices and staging uat sign-off documents.
  • docsmarkdown compiled to styled word files, synced to shared drives.
04

multi-stage verification & sanitization

  • contractsbusiness logic cross-checked against api models.
  • leaksevery document checked for personal data and credentials.
  • loopfailures quarantined and returned to the operator.

tier one, the intake gatekeeper, audits raw context before anything is drafted. it scans briefs for indonesian pii and private credentials, splits fuzzy requirements into must-have, should-have and strictly out-of-scope won't-have items, and interrupts with edge-case questions. if a brief says users receive marketing vouchers, it asks: can a voucher discount exceed cart value, are vouchers stackable with member tier points, and what http error code is returned on concurrency collisions.

tier two scaffolds three synchronized artifacts: a brd with journeys, edge cases, soft api contracts and explicit state machines, for example pending reconciliation to invoiced to disputed; system flowcharts; and lightweight mobile prototypes.

tier three handles acceptance: berita acara acceptance documents with test matrices and uat sign-off, and markdown specs compiled into styled word documents placed in synced shared drives.

tier four keeps every artifact provisional until it clears validation: contract consistency, leak prevention, and an automated correction loop that quarantines failures and returns them to the operator.

(07)the stack[ product operations ]

ordinary tools, strict wiring.

  • agentic orchestrationgoogle antigravity (agy) sdk and a custom multi-agent skill system in .agents/skills/.
  • specification layermarkdown-as-code versioned in git: pull request reviews, diffs and audit trails for product specs.
  • document generationpython python-docx engine with xml style injection.
  • sanitization & lintingcustom python regex analyzers that verify privacy compliance.
  • interactive prototypingresponsive html, css and svg mobile prototypes for pre-sprint alignment.

the stack is deliberately ordinary. orchestration runs on the google antigravity sdk with a custom multi-agent skill system. specs are markdown versioned in git, so they get pull request reviews, diffs and audit trails like code.

documents are generated with python-docx, sanitization runs through custom python analyzers, and prototypes are plain html, css and svg.

the takeaway[ product operations ]

constrain before you generate.

don't use ai as a chatbot for generic prose. give it strict scope, enforce edge-case audits, embed domain standards in the tools, and verify every output against engineering constraints.

if you take one lesson from this system: do not use ai as a conversational chatbot to write generic prose.
