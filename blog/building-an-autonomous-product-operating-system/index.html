How I Designed the MAPCLUB Product Operating System: Beyond LLM Slop to Verified Enterprise Blueprints

By Ramadhana Bhanuharya Krishnamurti (Krishna / naquuuu) • Technical Product Owner

💡 The Core Thesis in 30 Seconds

Asking generic AI chatbots to "write a PRD" produces unbuildable AI Slop—fluffy buzzwords with missing database schemas, vague scopes, and zero API contracts that crumble under real engineering review. In this essay, I open-source the architectural reasoning behind C:\work\mapclub-po-workspace: an autonomous multi-agent operating system that transforms chaotic business requests into deterministic, zero-defect enterprise specifications.

1. The Problem: Why Chatbots Fail in Enterprise Product Management

In high-scale enterprise environments like MAPCLUB—where software connects hundreds of premier retail brands to millions of consumers—a single ambiguous requirement can halt development sprints or cause multi-million rupiah financial reconciliation discrepancies.

The typical problem in modern tech teams looks like this:

  1. Raw Stakeholder Input is Chaotic: A business brief arrives as an unformatted Slack message, a messy meeting transcript, or a bulleted wishlist with contradictory goals.
  2. Prompt Engineering Produces "AI Slop": Feeding that brief into ChatGPT or Claude produces a superficial 10-page document filled with consultant fluff: "The system will provide an intuitive, scalable, AI-driven experience."
  3. Engineers Hit a Wall: When software developers receive this, they can't write a single line of code because fundamental questions are unanswered:
    • What is the exact JSON request/response schema?
    • What happens when a database transaction times out after 3,000ms?
    • How does the billing service reconcile discount vouchers stacked with loyalty points?

Comparing Two Paradigms: Fragile Slop vs. Deterministic Workspace

The difference between treating AI as a conversational toy vs. an engineered compiler.
✕ THE FRAGILE AI SLOP LOOP (WHAT MOST TEAMS DO)
Messy Slack Chat → Naive LLM Prompt → Generic 10-page Buzzword Document → Engineering Rejection → Weeks of Manual Clarification Meetings.
✓ THE DETERMINISTIC MAPCLUB PIPELINE (HOW I ARCHITECTED IT)
Raw Brief → Agent Intake Audit (Strict MoSCoW Bounds) → Soft API Contract Extraction → Deterministic Anti-Slop Specification → Automated BAC/UAT Sign-off → Verified Code Deployment.

2. Inside the Architecture: How C:\work\mapclub-po-workspace Works

To solve this permanently, I architected a local, agentic Product Operating System inside mapclub-po-workspace. It is organized into specialized agent skills, strict templates, and automated validation scripts:

Tier 1: Boundary Audit & Intake Gatekeeper (mapclub-intake)

Before any specification is drafted, the intake skill aggressively audits the raw context. It acts like a strict border guard:

  • MoSCoW Enforcement: Separates fuzzy requirements into rigid boundaries: Must-Have (P0 MVP), Should-Have, and strictly out-of-scope Won't-Have items.
  • Proactive Edge Case Auditing: If a brief mentions "users receive marketing vouchers", the agent interrupts and demands answers: "Can a voucher discount exceed cart value? Are vouchers stackable with member tier points? What exact HTTP error code is returned on concurrency collisions?"

Tier 2: The Anti-Slop BRD Engine (mapclub-brd & 09_new_anti_slop_brd_prompt.txt)

Once boundaries are locked, the BRD generation skill compiles the specification adhering strictly to our internal engineering standards (PO_STANDARDS.md):

  • Soft API Contracts: Every feature includes precise JSON request and response payloads with parameter data types (UUID, ISO-8601 strings, integers) and realistic edge-case responses.
  • Database Entity State Machines: Defines explicit database statuses (e.g., PENDING_RECONCILIATION → INVOICED → DISPUTED) so backend engineers know exactly what state transitions to handle.
  • Zero Consulting Slop: All adjectives and marketing buzzwords are banned. The document is written like a mathematical specification.

Tier 3: Acceptance Governance & UAT Pipeline (mapclub-bac & mapclub-sharepoint)

Writing requirements is only half the battle; getting executive and cross-departmental approval is the other:

  • Berita Acara Acceptance (BAC): Automatically synthesizes test matrices and staging UAT sign-off documentation formatted for corporate governance.
  • Automated Word & SharePoint Sync: Compiles Markdown specifications into official Microsoft Word deliverables (.docx) styled with MAPCLUB corporate typography, tables, and executive sign-off signatures, deposited directly into synced SharePoint drives.

Tier 4: Automated Verification & Sanitization Gate

To prevent accidental data leakage or broken specs, the workspace includes custom Python validation scripts:

  • verify_sanitization.py: Scans every markdown file and artifact before git commits, guaranteeing strictly zero Indonesian PII (NIK, phone numbers), production API keys, or confidential financial tokens ever enter version control.
  • Deterministic regression test suites validating formatting and table integrity.

3. The Underlying Technology Stack

The workspace was constructed utilizing modern systems tools:

  • Agentic Orchestration: Google Antigravity (AGY) SDK & IDE custom multi-agent skill system (.agents/skills/).
  • Specification Layer: Markdown-as-Code versioned directly in Git, enabling pull request reviews, diff tracking, and audit trails for product specs.
  • Document Generation: Python python-docx engine with corporate XML style injection.
  • Sanitization & Linting: Custom Python regex analyzers verifying privacy compliance.
  • Publishing Engine: Automated background synthesis engine running weekly cron schedules.

4. The Core Lesson: AI is a Compiler, Not a Chatbot

If you take one lesson away from this architecture, let it be this:

Do not use AI as a conversational companion to write generic prose.

Treat AI as a deterministic compiler: give it strict constraints, enforce boundary audits, embed your company's domain standards into its tools, and verify every single output against real-world engineering constraints. That is how you build systems that don't break.
